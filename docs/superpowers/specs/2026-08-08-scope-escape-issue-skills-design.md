## 0. 요약

스킬 두 개를 만든다.

| 슬러그 | 역할 |
| --- | --- |
| `scope-escape-issue` | 현재 브랜치의 범위를 벗어난 발견을 감지해 이슈로 뺄지 묻고, 승낙하면 `gh issue create` 로 발행한다 |
| `issue-to-pr` | 이슈 번호를 받아 읽고, 좌표 유효성을 확인하고, 구현·검증·커밋한 뒤 승인을 받아 PR 을 연다 |

두 스킬은 **이슈 본문의 정형**으로만 이어진다. 발행이 쓰고 처리가 읽는다.

두 벌을 만든다 — devkit 템플릿(`templates/_skills/`, 소비자 프로젝트로 배포)과 전역 gstack(`~/.claude/skills/`). 두 벌의 동일성은 강제하지 않는다.

## 1. 실측 (2026-08-08)

상상하지 않고 실물을 먼저 읽었다. **네 군데에서 설계가 바뀌었다.**

### 1.1 소비자 `CLAUDE.md` 에는 브랜치·worktree 규약이 없다

`git grep -i -E 'worktree|브랜치|branch' origin/main -- packages/devkit-cli/templates/nest/CLAUDE.md` 가 **0건**이다. worktree 규칙은 사용자 전역 `CLAUDE.md` 에만 있다.

따라서 `issue-to-pr` 의 devkit 판이 worktree 생성을 지시하면, **소비자에게 존재한 적 없는 규약을 스킬이 임의로 강제**하는 것이 된다. 그것이 [oxlint 게이트 주장 드리프트]가 남긴 결함의 형태 그대로다 — 문서가 없는 전제를 근거로 삼는 것. 두 벌이 여기서 갈린다(6.3절).

### 1.2 전역에는 `~/.claude/commands/` 가 없다

`ls ~/.claude/commands` 가 `No such file or directory` 다. 반면 devkit 은 `templates/_shared/.claude/commands/` 에 `verify.md`·`review.md` 를, 유형별로 네 개를 더 배포한다.

그리고 **스킬은 그 자체로 `/<슬러그>` 로 호출된다.** 즉 4번 결정("스킬 + 슬래시 커맨드")이 반드시 별도 커맨드 파일을 뜻하지는 않는다. 커맨드 파일의 고유한 값은 **인자를 받는 것**이다(`/issue-work 12`).

결론: 커맨드 파일은 devkit 에만 둔다. 전역은 스킬 두 개로 끝난다. 없는 디렉토리를 새로 만들 이유가 없다.

### 1.3 배선은 이미 깔려 있다 — 새로 할 일이 없다

스킬 설계가 남긴 자산이 새 파일을 그대로 받는다.

- `src/lib/categories.ts` 의 패턴이 `^\.claude\/(?:agents|commands|skills)\/.+` → `claude` 다. 새 커맨드·스킬은 아무 조치 없이 `devbak update --only claude` 의 대상이 된다.
- `templates/_shared/_gitignore` 의 devkit 블록이 `!.claude/`·`.claude/*` 뒤에 `!.claude/agents/`·`!.claude/commands/`·`!.claude/skills/` 를 둔다. 새 파일이 조용히 무시되는 함정은 닫혀 있다.

### 1.4 squash 머지가 SHA 조상 검사를 무력화한다

이 저장소는 PR 을 squash 로 머지하고 브랜치를 지운다. 그 결과 **머지된 브랜치의 커밋은 `main` 의 조상이 아니다.** PR #10 이 실례다 — `feature/devkit-claude-skills` 의 커밋 12 개는 내용이 전부 `origin/main` 에 있는데도(`git diff --stat origin/main <브랜치>` 에 해당 파일이 하나도 안 나온다) 조상 관계는 없다.

따라서 `git merge-base --is-ancestor <발견SHA> HEAD` 를 유효성 게이트로 쓰면 **정상 상황에서 매번 "좌표가 낡았다"고 오경보**한다. 더구나 브랜치가 삭제·GC 되면 그 SHA 는 존재하지 않는 객체가 되어 검사 자체가 불가능해진다.

이것이 4.3절에서 SHA 를 게이트가 아니라 **단서**로 격하시킨 근거다.

## 4. 이슈 본문 계약

두 스킬을 잇는 **유일한** 인터페이스다.

### 4.1 제목

명령형 한 줄, 한글. 커밋 메시지 규약과 같은 톤.

> 전역 설치된 devbak 이 아무 출력 없이 끝나는 것을 고친다

### 4.2 본문

```markdown
## 무엇을
<한 문장. 무엇을 바꿔야 하는가>

## 왜 지금이 아닌가
<현재 브랜치가 하려던 일과 어떻게 다른지. 판정 근거를 그대로 남긴다>

## 발견 좌표
- 커밋: `<발견 시점 git rev-parse HEAD>`
- 브랜치: `<발견 시점 브랜치 이름>`
- 파일: `path/to/file.ts:120`, `other.ts:44`

## 제안 방향
<2-3줄. 선택하지 않은 길이 있으면 왜 아닌지도>

## 무엇으로 다 됐다고 판단하나
<확인 방법. 테스트·명령·관찰 가능한 결과>

<!-- scope-escape-issue -->
```

마지막 HTML 주석이 서명이다. 처리 스킬은 이것으로 "정형 본문"임을 안다. 저장소 설정을 전혀 건드리지 않는 식별자다.

### 4.3 SHA 는 게이트가 아니라 단서다

1.4 절의 실측 때문에, 처리 스킬의 좌표 확인은 세 갈래다.

1. `git cat-file -e <SHA>` — 커밋이 로컬에 있는가
2. **있으면** → `git log <SHA>..HEAD -- <파일들>` 로 그 파일들이 그 뒤 바뀌었는지 본다. 바뀌었으면 본문의 라인 번호를 믿지 않고 재탐색한다.
3. **없으면** → "좌표를 검증할 수 없다"고 **명시하고**, 본문을 단서로만 써서 처음부터 탐색한다.

3 번이 규칙의 핵심이다. **확인하지 못했으면 확인하지 못했다고 말한다.** 검증할 수 없을 때 조용히 통과시키는 것이 이 저장소가 반복해서 데인 형태다.

### 4.4 라벨을 쓰지 않는다

`gh issue create --label` 은 그 라벨이 저장소에 미리 존재해야 한다. `devbak create` 로 갓 만든 저장소에는 커스텀 라벨이 없다. 라벨을 쓰려면 `gh label create` 로 **저장소 설정을 바꾸는 부작용**이 붙는다.

그리고 처리 스킬은 사용자가 번호를 주므로 목록 탐색이 필요 없다 — 라벨이 해결할 문제가 없다.

> 구현 계획에서 `--label` 의 실패 동작을 실제 호출로 한 번 확인한다. 이 절의 전제가 틀렸다면 근거를 고친다.

## 5. 발행 스킬 — `scope-escape-issue`

### 5.1 언제 도는가 — "발견 즉시"가 아니라 체크포인트

이 스킬은 기존 43 개와 발동 성격이 다르다. 보통 스킬은 **사용자가 말한 것**에 걸리지만("의존성 추가", "테스트 먼저"), 이것은 **모델 자신의 관찰**에 걸려야 한다. "발견하는 즉시 떠올려라"는 규율은 지킬 시점이 특정되지 않아 사실상 지켜지지 않는다.

그래서 시점을 고정한다: **작업 단위를 마치고 사용자에게 보고하기 직전.** 커밋 직전, 검증 통과 후, 턴을 끝내기 전 — 이미 멈춰 서서 돌아보는 지점이라 규율을 끼워 넣을 자리가 있다.

`APPLIES:` 가 그 상황을 서술하고, `/issue` 커맨드가 백업이다.

### 5.2 판정 — 브랜치 이름이 선언된 범위다

1. `git rev-parse --abbrev-ref HEAD`
2. 이름이 주제를 담는가?
   - `fix/devbak-symlink-entrypoint` → 담는다. "전역 devbak 진입점 수정"이 선언된 범위다.
   - `main`, `worktree-cozy-painting-sparkle` → 담지 않는다(기본 브랜치이거나 자동 생성).
3. 담지 않으면 → 그 세션에서 **한 번만** 묻는다. "지금 작업을 한 문장으로 뭐라고 할까요?" 받은 답을 이후 판정에 쓴다. 답은 **대화 맥락에만 유지한다** — 파일로 저장하지 않는다. 저장하면 그 파일이 다음 작업에서 낡은 범위를 주장하게 되고, 아무도 갱신하지 않는다.
4. 발견한 것이 그 범위 안인가?

근거: 이 저장소의 브랜치 규약(`feature/*`·`fix/*`·`chore/*`)이 실제로 지켜진다. 머지된 PR 10 건이 전부 주제를 이름에 담고 있다. **선언 절차를 새로 만드는 대신 이미 존재하는 선언을 재사용한다.**

### 5.3 무엇을 찾는가 — 유형과 반례

반례가 없으면 전부 이슈로 빠져나가 작업이 끝나지 않는다. 유형마다 "이건 지금 한다"를 함께 적는다.

| 유형 | 이슈로 | 지금 한다 |
| --- | --- | --- |
| 무관한 버그 | 지금 작업과 코드 경로가 겹치지 않음 | 그 버그가 지금 작업을 **막고 있음** |
| 문서-실물 불일치 | 다른 문서·다른 유형의 이야기 | 지금 고치는 코드가 그 문서의 근거임 |
| 없는 가드·테스트 | 지금 결함과 다른 종류를 막는 것 | 지금 고친 결함의 **재발 방지** |
| 같은 결함의 다른 사례 | 다른 패키지·다른 유형에도 있음 | 같은 파일·같은 함수 안 |
| 리팩터 기회 | 파일이 커졌다, 이름이 나쁘다 | 지금 편집하는 그 자리가 걸림돌 |

세 번째 줄이 특히 자주 나온다. "재발 방지 테스트는 지금 같이"는 이미 여러 번 그렇게 해 왔고(`d8c336a` 버전 리터럴 가드), 그것이 옳다.

### 5.4 묻고 · 발행하고 · 즉시 복귀

발견을 보고하고 세 갈래로 묻는다: **1) 지금 고친다 · 2) 이슈로 발행 · 3) 넘어간다.**

**묻는 도구는 스킬이 규정하지 않는다.** 사용자 전역 규칙에 "텔레그램 세션에서는 `AskUserQuestion` 금지"가 있어, 스킬이 도구를 못 박으면 그 규칙과 충돌한다.

발행이면:

1. `gh issue list --state open --search "<핵심어>"` 로 **같은 이슈가 이미 있는지** 훑는다. 있으면 새로 만들지 않고 알린다.
2. `gh issue create --title "..." --body-file -` 로 **stdin** 으로 본문을 넘긴다.

`--body-file -` 은 취향이 아니라 사고 예방이다. 본문에 백틱·개행이 많아 `--body` 인라인은 깨지기 쉽고, 임시 파일은 **저장소 안에 만들면 자동 훅이 커밋한다**(실제 사고 기록이 있다). stdin 은 파일을 아예 만들지 않는다.

발행 후 이슈 번호와 URL 만 보고하고 **원래 작업으로 즉시 복귀한다.** 만든 이슈를 그 자리에서 처리하러 가지 않는다 — 그러면 스킬이 막으려던 바로 그 일을 스킬이 하게 된다.

### 5.5 `gh` 를 쓸 수 없을 때

인증이 없거나 리모트가 없으면 멈추고 보고하되, **발견 내용은 대화에 그대로 남긴다.** 이슈를 못 만들었다고 발견까지 버리면 원래 문제로 돌아간다. 이것은 폴백이 아니라 유실 방지다.

## 6. 처리 스킬 — `issue-to-pr`

### 6.1 읽는다

`gh issue view <N> --json title,body,state,url,comments`

- `state` 가 `CLOSED` 면 멈춘다.
- **댓글도 읽는다.** 이슈는 댓글에서 방향이 뒤집히는 일이 흔해, 본문만 읽으면 이미 폐기된 계획을 구현한다.
- 서명(`<!-- scope-escape-issue -->`)이 있으면 정형으로 파싱하고, **없으면 자유 본문으로 취급한다.** 사람이 손으로 연 이슈도 처리할 수 있어야 한다. 정보가 모자라면 묻는다.

### 6.2 좌표를 확인한다

4.3 절의 세 갈래.

### 6.3 작업 공간을 만든다 — 두 벌이 갈리는 유일한 지점

| | 방식 |
| --- | --- |
| 전역판 | `git worktree add` + `origin/main` 위 rebase (사용자 `CLAUDE.md` 의 worktree 규칙) |
| devkit 판 | `origin/main` 에서 `git switch -c <접두>/<슬러그>` (소비자에겐 worktree 규약이 없다 — 1.1절) |

브랜치 이름은 이슈 제목에서 슬러그로 만들고, 접두는 이슈의 성격을 따른다 — 결함이면 `fix/`, 새 기능이면 `feature/`, 그 밖은 `chore/`. 그러면 **그 이름이 곧 발행 스킬의 "선언된 범위"가 된다**(5.2절). 처리 중에 또 딴 것이 보이면 발행 스킬이 그 이름을 근거로 다시 판정한다. 두 스킬이 서로의 입력을 만들어 폐곡선이 된다 — 따로 맞춘 것이 아니라 A 안을 고른 결과다.

### 6.4 구현한다

**방법을 새로 규정하지 않는다.** 프로젝트에 이미 있는 것을 쓴다 — `tdd`, `verify-implementation`, 그리고 의존성·설정을 건드리면 `devkit-stack` 이 이긴다. 처리 스킬이 구현 방법론까지 담으면 43 개 스킬과 충돌하는 44 번째 의견이 된다.

### 6.5 검증한다

`/verify` 가 이미 `pnpm lint` → `pnpm build` → `pnpm test` 를 순서대로 돌리고 실패 지점에서 멈춘다. 재사용한다. 그 문서에 이미 있는 문구가 그대로 적용된다 — "종료 코드 0 이라는 것만으로 통과를 보고하지 않는다."

### 6.6 커밋한다

한글 imperative, 본문에 **왜**.

### 6.7 푸시하고 PR 을 연다 — 승인 후에만

소비자 템플릿에는 `claude-review.yml` 과 `auto-merge.yml` 이 **함께** 배포된다. PR 을 열면 → Claude 가 리뷰하고 Commit Status(`claude-review`)를 남기고 → `auto-merge` 가 그 신호를 읽어 rebase 로 머지한다.

즉 이 환경에서 "PR 생성까지"는 사실상 **"머지까지"** 이며, 사람이 개입할 지점이 없다.

그래서 **푸시·PR 생성 직전에 승인을 받는다.** 6.6 절까지는 승인 없이 진행하고, 외부로 나가는 순간에만 멈춘다. 자동화 수준은 그대로고 멈추는 지점만 하나 생긴다.

PR 본문에 `Closes #N` 을 넣는다.

### 6.8 실패했을 때

검증이 깨지면 **멈추고 보고한다.** 이슈를 닫지 않고, PR 도 열지 않고, "일부는 됐다"고 뭉개지 않는다.

## 7. devkit 배선과 테스트

### 7.1 바꾸는 것

```
src/lib/skill-sets.ts       COMMON 에 2개 추가
tests/skill-assets.test.ts  풀 43→45 · nest 23→25 · next 26→28 · monorepo 43→45
tests/__snapshots__/recipe-{nest,next,monorepo}.test.ts.snap   -u
```

`COMMON` 을 통해 세 유형에 모두 들어가므로 `recipes/*.ts` 세 파일은 손대지 않는다.

### 7.2 새로 넣는 가드

**① 계약 드리프트 가드 — 가장 중요하다.**

두 스킬의 유일한 인터페이스(4.2절)가 **문서 두 벌에 나뉘어 손으로 적힌다.** 발행이 `## 발견 좌표` 라고 쓰고 처리가 `## 발견 위치` 를 찾으면, 둘 다 문법적으로 멀쩡하고 테스트도 초록이며 **실패는 실제로 이슈를 처리할 때야 드러난다.** "한 사실이 세 곳인데 둘만 갱신"과 같은 형태다.

대조 방법은 이렇다. 두 `SKILL.md` 는 각자 본문 정형을 인용한 코드 블록을 갖는다(발행은 "이렇게 쓴다", 처리는 "이런 섹션을 읽는다"). 테스트가 **각 문서의 그 코드 블록에서 `^## ` 제목을 뽑아 두 집합이 같은지** 본다. 한쪽에만 있는 제목이 하나라도 있으면 실패하고, 메시지에 그 제목을 찍는다.

두 문서 모두 손으로 쓴 별개 문자열이라 자기 참조가 아니다 — 한쪽만 고치면 실제로 깨진다. 구현 시 한쪽 제목을 바꿔 **실제로 깨지는지 변이로 확인한다.** 통과하는 테스트는 증거가 아니다.

**② 이름 실재 가드**

두 스킬이 풀에 있고 세 유형에 모두 선택되는가. 단, **하드코딩한 이름으로** 단언한다. `SKILL_SETS` 를 `SKILL_SETS` 와 비교하면 스킬을 빼도 깨지지 않는 자기 참조가 된다.

**③ git 추적 실측**

새 커맨드·스킬 파일에 `git check-ignore` 를 직접 묻는다. 이 저장소가 두 번 데인 지점이고(`.claude/` 조상 무시 줄), 문자열 `toContain` 으로는 드러나지 않는다.

**④ e2e**

`devbak create` 후 `.claude/skills/scope-escape-issue/SKILL.md` 와 `.claude/commands/issue.md` 가 실재하는가.

### 7.3 gstack 쪽

테스트 인프라가 없는 저장소다. 파일 두 개를 손으로 추가하고 끝낸다.

### 7.4 두 벌 동일성은 검증하지 않는다

devkit CI 러너에 gstack 저장소가 없으므로 바이트 비교 테스트를 돌릴 수 없다. **이 경계에는 기계 가드를 걸 수 없다.** 그래서 5 번 결정이 동일성을 요구하지 않는다 — 지킬 수 없는 규칙을 세우지 않는다.
