# CI 자동 버전 올림과 게시 설계

**날짜**: 2026-08-06
**상태**: 승인됨
**선행**: [devkit-cli 게시 가능화](2026-08-05-publishable-cli-design.md), [레지스트리 설치 전환](2026-08-05-registry-install-design.md)

## 1. 문제

버전을 손으로 올리고 게시도 손으로 한다. 그 결과 두 가지가 생겼다.

- **게시본이 낡는다.** `@cheolubak/devkit-cli@0.1.0` 이 게시된 뒤 `packages/devkit-cli`
  에만 11개 커밋이 쌓였다. `pnpm dlx` 로 받으면 옛 템플릿이 온다.
- **락스텝이 조용히 깨졌다.** 설정 패키지 6개 중 `vitest-config` 만 `0.1.1` 이고
  나머지는 `0.1.0` 이다. 손으로 올리다 보니 어긋난 것을 아무도 막지 않았다.

이 저장소에는 **CI 워크플로가 하나도 없다.** 검증도 게시도 전부 로컬 실행에
의존한다.

## 2. 결정

**`main` 에 push 되면 GitHub Actions 가 검증하고, 버전을 올리고, 게시한다.**

### 2.1 흐름

```
main push
  ↓
① 릴리스 대상 판정 — 지난 릴리스 태그 이후 커밋에서
   어느 축이 바뀌었는지(경로) · 얼마나 올릴지(커밋 접두) 계산
  ↓ (대상 없으면 종료)
② 전체 검증 — build → test → typecheck → lint:ox → lint:es → test:e2e
  ↓ (하나라도 실패하면 게시하지 않고 종료)
③ 버전 갱신 — package.json, 필요하면 DEVKIT_VERSION_RANGE
  ↓
④ 게시 — pnpm publish
  ↓
⑤ 커밋 + 태그를 main 에 push (`[skip ci]`)
```

**순서가 요구다.** 검증이 깨지면 아무것도 나가지 않고, 게시가 실패하면 버전
커밋도 남지 않는다 — 저장소가 "올렸다고 하는데 레지스트리엔 없는" 상태가
되지 않는다.

### 2.2 두 릴리스 축

| 축 | 대상 | 태그 |
| --- | --- | --- |
| 설정 | 6개 **락스텝** — 하나만 바뀌어도 함께 올린다 | `config-vX.Y.Z` |
| CLI | `devkit-cli` 단독 | `cli-vX.Y.Z` |

**락스텝을 택한 이유**: 생성물이 선언하는 범위가 `DEVKIT_VERSION_RANGE` 상수
**하나**다. 6개가 각자 다른 마이너로 흩어지면 상수 하나로 표현할 수 없다.
6개는 서로 import 하지 않고 함께 소비되므로 함께 굴려도 실질 피해가 없다.

`devkit-cli` 는 독립이다 — 아무도 의존으로 선언하지 않고
`registry-version.test.ts` 의 대상도 아니다. `templates/` 가 이 패키지 안에
있으므로 **템플릿만 바뀌면 CLI 축만 돈다.**

### 2.3 무엇이 릴리스를 부르는가

**릴리스 여부는 경로로, 올림 크기는 커밋 접두로** 정한다.

**경로** — 각 패키지에서 **게시되는 것에 영향을 주는 변경**만 센다. 아래는
제외한다(tarball 에 안 들어가거나 동작을 바꾸지 않는다):

```
tests/**  README.md  eslint.config.mjs  vitest.config.ts
tsconfig.json  tests/tsconfig.json  tsup.config.ts  turbo.json
```

**크기** — 대상 축을 건드린 커밋들의 접두 중 가장 큰 것:

| 접두 | 올림 |
| --- | --- |
| 본문에 `BREAKING CHANGE:` | major |
| `feat:` | minor |
| `fix:` · `refactor:` · `perf:` · `build:` | patch |
| `docs:` · `test:` · `chore:` · `style:` | 없음 |

경로는 걸렸는데 크기가 "없음"뿐이면 릴리스하지 않는다. 이 저장소는 이미 이
접두를 일관되게 쓰고 있어 새 규율이 필요 없다.

### 2.4 `DEVKIT_VERSION_RANGE` 자동 갱신

설정 축이 **마이너 이상을 올릴 때만** `^0.X.0`(또는 `^X.0.0`)으로 함께
갱신한다. 패치면 그대로 둔다 — 캐럿이 이미 흡수한다.

이걸 안 하면 다음 CI 실행의 `registry-version.test.ts` 가 막는다. 관문이
자동화를 막는 것이 아니라, **자동화가 관문을 만족시키도록** 만드는 것이 요점이다.

### 2.5 부트스트랩 (도입 시 한 번)

지금 락스텝이 깨져 있다(`vitest-config` 만 `0.1.1`). 도입 시:

1. 설정 패키지 6개를 **`0.1.1`** 로 맞춘다(가장 높은 버전 기준 — 이미 게시된
   `vitest-config@0.1.1` 을 되돌릴 수 없다).
2. 태그를 만든다: `config-v0.1.1`, `cli-v0.1.0`.

이것이 없으면 첫 CI 실행이 "지난 릴리스"를 찾지 못한다.

**`0.1.1` 로 맞추는 것은 게시를 뜻하지 않는다.** 부트스트랩은 저장소의 버전
표기와 태그만 정렬한다. 실제 게시는 다음 릴리스부터 CI 가 한다.

### 2.6 어디에 구현하나

**버전 판정 로직을 워크플로 YAML 의 bash 로 쓰지 않는다.** 이 저장소는 관문을
테스트로 고정해 왔는데 YAML 안의 bash 는 테스트가 안 된다.

`packages/devkit-cli/src/release/` 에 **순수 함수**로 둔다 — 커밋 목록과 변경
경로를 받아 "어느 축을 얼마나 올릴지"를 내는 함수. 단위 테스트가 접두 판정·경로
필터·락스텝·상수 갱신 규칙을 전부 고정한다. 워크플로는 그것을 호출만 한다.

tsup 이 `bin.ts`·`index.ts` 진입점만 번들하므로 **이 코드는 tarball 에 실리지
않는다.** 별도 패키지를 만드는 것보다 가볍다 — 새 패키지는
`package-task-coverage.test.ts` 가 요구하는 설정 일습(`eslint.config.mjs`·
`vitest.config.ts`·`lint`·`test`·`typecheck` 스크립트)이 딸려온다.

### 2.7 토큰

GitHub Actions 의 기본 `GITHUB_TOKEN` 에 `packages: write` 권한이 있어 **PAT 이
필요 없다.** 워크플로에 `permissions: { contents: write, packages: write }` 를
선언한다(`contents: write` 는 ⑤의 커밋·태그 push 용).

e2e 도 같은 토큰으로 `@cheolubak/*` 를 설치한다.

### 2.8 루프 방지

⑤의 커밋 메시지에 **`[skip ci]`** 를 넣는다. 그 커밋이 다시 워크플로를 돌리면
무한 루프가 된다.

## 3. 대가와 알려진 위험

- **게시가 중간에 실패하면 일부만 올라간다.** GitHub Packages 는 같은 버전
  재게시가 불가능하므로 재실행하면 이미 올라간 패키지에서 실패한다. 이 경우
  **커밋·태그를 남기지 않고 워크플로를 실패시켜** 사람이 개입하게 한다.
  자동 복구는 하지 않는다 — 되돌릴 수 없는 연산이다.
- **e2e 가 일시적으로 실패하면 릴리스가 막힌다.** ~3분이 걸리고 네트워크·
  레지스트리를 탄다. 재실행으로 풀리지만 릴리스가 지연된다. 깨진 것을 게시하는
  쪽보다 낫다고 판단했다 — 이 저장소에서 실제 결함을 잡은 것은 매번 e2e 였다.
- **한 패키지의 기능 추가가 설정 6개의 버전을 움직인다**(락스텝). 서로 의존이
  0 이고 함께 소비되므로 받아들인다.
- **`docs:` 커밋만 쌓이면 영원히 릴리스되지 않는다.** 의도된 동작이다. 필요하면
  `workflow_dispatch` 로 손으로 돌릴 수 있게 한다.

## 4. 완료 기준

1. `main` 에 `fix:` 커밋이 push 되면 해당 축의 **패치**가 올라가고 게시된다.
2. `feat:` 커밋이면 **마이너**가 올라가고, 설정 축이면 `DEVKIT_VERSION_RANGE`
   도 함께 갱신된다.
3. `docs:`·`test:` 만 있으면 **아무것도 게시되지 않는다.**
4. `tests/**` 나 `README.md` 만 바뀌면 릴리스되지 않는다.
5. 검증(`test`·`typecheck`·`lint:ox`·`lint:es`·`test:e2e`) 중 하나라도 실패하면
   **게시도 커밋도 일어나지 않는다.**
6. 게시 후 커밋·태그가 `main` 에 남고, 그 커밋이 워크플로를 다시 돌리지 않는다.
7. 버전 판정 로직이 **단위 테스트로 고정**된다 — 접두 판정, 경로 필터, 락스텝,
   상수 갱신, "릴리스 없음" 판정 각각.
8. 릴리스 코드가 게시 tarball 에 실리지 않는다.
9. 기준선 유지: `pnpm test`·`pnpm typecheck` 7/7·`pnpm lint:ox` 에러 0·
   `pnpm lint:es` 8/8·`pnpm test:e2e` 13/13.

## 5. 범위 밖

- CHANGELOG 자동 생성
- PR 단위 검증 워크플로(이 설계는 `main` push 만 다룬다)
- `devkit-cli` 를 npm 공개 레지스트리에 함께 게시
- 게시 실패 시 자동 롤백
