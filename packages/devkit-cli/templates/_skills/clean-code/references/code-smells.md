# 코드 스멜 카탈로그와 리팩터링 레시피

**코드 스멜**은 버그는 아니지만 더 깊은 설계 문제를 암시하는 표면 징후다. 스멜에 이름을 붙일 수 있으면 무엇을 어떻게 고칠지가 분명해진다. 리팩터링은 **테스트가 초록인 상태에서, 한 번에 하나씩** 적용한다(tdd 참조).

## 스멜 → 레시피 빠른 표

| 스멜 | 징후 | 주요 레시피 |
|------|------|------------|
| 긴 함수 (Long Function) | 스크롤해야 다 보임, 주석으로 구획 나눔 | 함수 추출 |
| 긴 파라미터 목록 | 인자 4개 이상 | 파라미터 객체 도입 |
| 중복 코드 | 같은 로직이 여러 곳 | 함수 추출 후 호출 |
| 거대 클래스 (God Class) | 필드·메서드가 수십 개, 책임 여러 개 | 클래스 추출, SRP 분리 |
| 기능 욕심 (Feature Envy) | 남의 객체 데이터를 계속 꺼내 씀 | 함수 이동 |
| 데이터 뭉치 (Data Clump) | 항상 함께 다니는 매개변수 3인방 | 객체로 묶기 |
| 원시값 집착 (Primitive Obsession) | `string` 하나로 이메일·전화·ID 다 표현 | 값 객체(Value Object) 도입 |
| 산탄총 수술 (Shotgun Surgery) | 한 변경에 여러 파일을 조금씩 고침 | 관련 로직 한 모듈로 모으기 |
| 분산된 조건문 | 같은 `switch(type)`이 여러 곳 | 다형성/전략으로 치환 |
| 주석으로 설명 | 블록마다 "이제 X를 함" 주석 | 함수 추출(이름이 주석 대체) |
| 죽은 코드 | 안 쓰이는 함수·변수·분기 | 삭제(git이 기억함) |
| 임시 필드 | 특정 상황에만 채워지는 필드 | 클래스/전략 추출 |

## 주요 스멜 상세

### 긴 함수
가장 흔하고 가장 중요한 스멜. **함수 안에 주석으로 "// 검증", "// 계산" 구획을 나눴다면**, 그 구획이 곧 추출 대상이다. 각 구획을 이름 있는 함수로 뽑으면 주석이 사라진다.

### 기능 욕심 (Feature Envy)
어떤 함수가 자기 클래스보다 **다른 클래스의 데이터**를 더 많이 만진다면, 그 함수는 데이터가 있는 곳으로 가야 한다.

```typescript
// ✕ Order의 데이터만 파고드는 로직이 엉뚱한 곳에
class Invoice {
  total(order: Order) {
    return order.items.reduce((s, i) => s + i.price * i.qty, 0) * (1 + order.taxRate);
  }
}
// ○ 계산을 데이터 주인에게로 이동 (함수 이동)
class Order {
  total() { return this.subtotal() * (1 + this.taxRate); }
}
```

### 원시값 집착 (Primitive Obsession)
도메인 개념을 `string`/`number`로만 표현하면 검증이 흩어지고 타입이 섞인다. **값 객체**로 승격하면 유효성이 한 곳에 모이고 타입이 잘못 섞이는 걸 컴파일러가 막는다.

```typescript
// ✕ 어떤 string이든 email 자리에 들어간다
function send(email: string) {}

// ○ 생성 시점에 검증되는 값 객체
class Email {
  private constructor(readonly value: string) {}
  static of(raw: string): Email {
    if (!raw.includes('@')) throw new InvalidEmailError(raw);
    return new Email(raw);
  }
}
```

### 분산된 조건문 → 다형성
같은 `switch (shape.type)`가 면적·둘레·그리기마다 반복되면, 타입 추가 때 모든 switch를 찾아 고쳐야 한다(OCP 위반). 다형성으로 치환하면 새 타입은 새 클래스 하나로 끝난다 — 이 전환의 원리와 OCP는 clean-architecture에서 다룬다.

## 핵심 리팩터링 레시피

- **함수 추출 (Extract Function)**: 코드 조각을 이름 있는 함수로. 가장 자주 쓰는 무기. 이름이 곧 주석이 된다.
- **함수 인라인 (Inline Function)**: 이름이 본문보다 정보가 적은 얇은 위임 함수는 도로 합친다(과다 추출 되돌리기).
- **변수 추출 (Extract Variable)**: 복잡한 식에 설명적 이름을 붙인다. `if (order.items.length > 0 && order.isPaid)` → `if (isShippable)`.
- **파라미터 객체 도입**: 함께 다니는 인자들을 타입으로 묶는다.
- **함수/필드 이동 (Move Function)**: 기능 욕심 해소. 데이터가 있는 곳으로 로직을 옮긴다.
- **조건문을 다형성으로 (Replace Conditional with Polymorphism)**: 타입 기반 분기를 전략/서브타입으로.
- **매직값을 상수로 (Replace Magic Literal)**: 리터럴에 이름을.
- **중첩 조건문을 가드 절로**: → [functions.md](functions.md) 참조.

## 리팩터링 규율

1. **안전망 먼저.** 리팩터링 대상에 테스트가 없으면 특성화 테스트(characterization test)로 현재 동작을 먼저 고정한다.
2. **작은 걸음.** 한 레시피 적용 → 테스트 → 커밋. 큰 리팩터링도 작은 안전한 단계의 연속이어야 한다.
3. **행동 변경과 구조 변경을 분리.** 리팩터링 커밋에는 기능 변경을 섞지 않는다("리팩터링"과 "기능 추가"는 다른 모자 — 동시에 쓰지 않는다).
4. **멈출 지점을 안다.** 가독성이 목표다. 더 쪼개도 이해가 나아지지 않으면 멈춘다. 과잉 추출(얇은 함수의 미로)은 그 자체로 스멜이다.

> 스멜은 "반드시 고쳐라"가 아니라 "여기를 보라"는 신호다. 트레이드오프를 따져 지금 고칠지, 티켓으로 남길지, 그대로 둘지 판단한다.
