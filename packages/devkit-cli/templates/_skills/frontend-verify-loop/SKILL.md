# 프론트엔드 검증 루프 (frontend-verify-loop)

프론트엔드 작업을 한 번에 다 하고 마지막에 몰아서 확인하지 않는다.
**작업을 논리적 청크로 쪼개고, 청크 하나를 끝낼 때마다 검증 게이트를 통과시킨 뒤에만 다음 청크로 넘어간다.** 이 스킬은 그 루프의 뼈대만 강제하고, 실제 검증은 기존 스킬/도구를 호출한다(오케스트레이터).

## 핵심 원칙

- **미검증 청크 위에 다음 청크를 쌓지 않는다.** 초록불을 확인하기 전에는 다음 작업을 시작하지 않는다. 깨진 토대 위에 쌓으면 실패 원인이 뒤섞여 디버깅 비용이 폭발한다.
- **검증은 매번, 작게.** 청크가 작을수록 실패 원인이 그 청크로 국소화되어 자동 수정이 쉬워진다.
- **이 스킬은 방법을 새로 가르치지 않는다.** 검증 방법은 이미 있는 스킬(tdd·eslint·e2e-mcp·design-review 등)에 있다. 여기서는 *언제·어떤 순서로 무엇을 호출할지*만 규율한다.

## 루프 (청크마다 반복)

```
청크 선언 → 구현 → 정적 게이트 → (UI 변경이면) 브라우저 게이트 → 초록 확인 → 커밋 여지 → 다음 청크
                         │                    │
                         └── 실패 ──► 자동 수정 → 재검증 (같은 실패 최대 3회, 초과 시 중단·보고)
```

### 1. 청크 선언
작업 전체를 논리적 청크(컴포넌트 하나 / 훅 하나 / 페이지 하나 / 상태 슬라이스 하나 / 기능 하나)로 쪼개 **TodoWrite로 나열**한다. 각 청크는 "그것만으로 검증 가능한 최소 단위"여야 한다. 너무 잘게(파일마다)도, 너무 크게(기능 전체를 한 청크로)도 쪼개지 않는다.

### 2. 구현
현재 청크 하나만 구현한다. 구현 중 도메인 지식이 필요하면 해당 스킬(react-best-practices·tanstack-query·framer-motion·nextjs-* 등)을 호출해 따른다.

### 3. 정적 게이트 (항상 실행)
아래 순서로 돌린다. **앞 단계가 초록이어야 다음 단계로 간다**(타입이 깨진 채 테스트를 돌리는 것은 시간 낭비).

```
typecheck  →  lint  →  build  →  test
```

- **명령 탐지**: `package.json`의 `scripts`에서 자동 탐지한다.
  - typecheck: `typecheck` / `type-check` 스크립트, 없으면 `tsc --noEmit`
  - lint: `lint` 스크립트 (oxlint+eslint 하이브리드면 그 명령)
  - build: `build` 스크립트
  - test: `test` 스크립트 (watch가 기본이면 `--run`/`--ci`/`--watch=false`로 1회성 실행)
- **폴백**: 스크립트가 없으면 저장소 관례인 `pnpm build` / `pnpm test` / `pnpm lint`를 쓴다. (이 저장소·사용자 규칙상 **항상 pnpm**, npm 금지.)
- **범위 최소화**: 가능하면 이번 청크와 관련된 테스트만 먼저 좁혀 돌리고(빠른 피드백), 청크 끝에서 전체를 한 번 확정한다.

### 4. 브라우저 게이트 (UI가 눈에 보이게 바뀐 청크만)
정적 게이트가 초록이어도 화면이 실제로 의도대로 뜨는지는 별개다. **렌더 결과가 바뀌는 청크**(새 컴포넌트·페이지·레이아웃·인터랙션)라면 Playwright MCP로 해당 화면을 열어 **스모크 체크**한다.

- ① 콘솔 에러/경고 0건인가 (`browser_console_messages`)
- ② 의도한 핵심 요소가 실제로 렌더되는가 (`browser_snapshot`으로 확인)
- ③ 핵심 상호작용 1개가 동작하는가 (클릭/입력 → 기대 반응)

순수 로직·유틸·타입·설정만 바뀐 청크는 브라우저 게이트를 건너뛴다(불필요한 비용).

**더 깊은 검증이 필요하면 위임한다** — 여기서 재구현하지 않는다:
- 시나리오·성능·네트워크까지 보는 실 e2e → **e2e-mcp**
- 간격·정렬·위계 등 픽셀 시각 QA + 자동 수정 → **design-review** (gstack)
- 색상·브랜드 적합성 진단 → **design-fit-review**
- 1인칭 사용자 감정·마찰 재연 → **ux-walkthrough**

### 5. 실패 처리 (자동 수정 루프)
게이트가 실패하면 멈추지 말고 고친다.

1. 실패 출력을 읽고 원인을 특정한다.
2. 수정한 뒤 **실패한 그 게이트부터** 재실행한다.
3. 초록이면 다음 단계로, 아니면 반복한다.

**안전장치 — 무한 루프 방지:**
- **같은 실패가 3회 연속** 재현되면 자동 수정을 멈추고, 시도한 내용·현재 에러를 사용자에게 보고한 뒤 지시를 기다린다.
- 포맷/린트/단순 타입 오류처럼 명백한 것은 그냥 고친다. 그러나 **테스트 로직 자체가 틀렸는지, 아키텍처 결정이 필요한지** 판단되는 실패는 3회를 기다리지 말고 조기에 멈추고 묻는다. (테스트를 통과시키려 프로덕션 의도를 왜곡하거나, 테스트를 무력화(skip/삭제)해서 초록을 만드는 것은 금지.)

### 6. 초록 확인 → 커밋 여지 → 다음 청크
- 모든 게이트가 초록이면 해당 Todo를 완료 처리한다.
- 사용자가 커밋을 원했거나 청크가 논리적 커밋 단위면, 이 지점이 자연스러운 커밋 포인트다(사용자 규칙: rebase 전용, imperative 메시지). 요청 없이 임의 커밋하지 않는다.
- 다음 청크로 이동해 2번부터 반복한다.

## 세션 예시

> 사용자: "상품 목록 페이지랑 필터 사이드바 만들어줘. 만들면서 검증해."

1. **청크 나열(TodoWrite)**: ① `ProductCard` 컴포넌트 ② `useProducts` 훅(데이터 페칭) ③ 목록 페이지 ④ `FilterSidebar` ⑤ 필터↔목록 연동
2. **청크 ①**: `ProductCard` 구현 → typecheck·lint·build·test 초록 → 브라우저로 카드 단독 렌더 확인 → ✅ → 다음
3. **청크 ②**: `useProducts` 구현 → 타입 에러 발생 → 자동 수정 → 재검증 초록 → (UI 없음, 브라우저 게이트 skip) → ✅
4. **청크 ③**: 페이지 구현 → 정적 초록 → 브라우저에서 목록 렌더+콘솔 에러 0 확인 → ✅
5. **청크 ④~⑤**: 동일 루프. ⑤에서 필터 클릭 시 목록 갱신을 브라우저 상호작용으로 확인.
6. 전체 청크 완료 후 마지막에 전체 test·build 한 번 확정.

## 이 스킬을 쓰지 않는 경우

- **테스트를 먼저 써서 구현을 이끌고 싶다** → `tdd`가 주도(레드-그린-리팩터). 이 스킬은 구현 후 게이트(test-after)다.
- **검증 없이 그냥 써보며 UX만 느끼고 싶다** → `ux-walkthrough`.
- **검증 도구 자체를 설정/구성**하려는 것 → `eslint`·`prettier`·`nextjs-testing`.
- **백엔드(NestJS) 작업** → 동일한 검증 루프는 `backend-verify-loop`.
