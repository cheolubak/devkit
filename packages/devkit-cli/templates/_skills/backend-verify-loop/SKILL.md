# 백엔드 검증 루프 (backend-verify-loop)

백엔드 작업을 한 번에 다 하고 마지막에 몰아서 확인하지 않는다.
**작업을 논리적 청크로 쪼개고, 청크 하나를 끝낼 때마다 검증 게이트를 통과시킨 뒤에만 다음 청크로 넘어간다.** 이 스킬은 그 루프의 뼈대만 강제하고, 실제 검증은 기존 스킬/도구를 호출한다(오케스트레이터). `frontend-verify-loop`의 백엔드(NestJS) 대응판이다.

## 핵심 원칙

- **미검증 청크 위에 다음 청크를 쌓지 않는다.** 초록불을 확인하기 전에는 다음 작업을 시작하지 않는다. 깨진 토대 위에 쌓으면 실패 원인이 뒤섞여 디버깅 비용이 폭발한다.
- **검증은 매번, 작게.** 청크가 작을수록 실패 원인이 그 청크로 국소화되어 자동 수정이 쉬워진다.
- **컴파일 초록 ≠ 런타임 정상.** 타입·빌드가 통과해도 DI 컨테이너가 실제로 뜨는지는 별개다(순환 의존성·모듈 미등록·프로바이더 누락·환경변수 부재는 런타임에서만 터진다). 그래서 정적 게이트에 더해 **부팅+요청 스모크**를 둔다.
- **이 스킬은 방법을 새로 가르치지 않는다.** 검증 방법은 이미 있는 스킬(tdd·nestjs-testing·eslint 등)에 있다. 여기서는 *언제·어떤 순서로 무엇을 호출할지*만 규율한다.

## 루프 (청크마다 반복)

```
청크 선언 → 구현 → 정적 게이트 → (요청 경로가 생기면) 런타임/API 게이트 → 초록 확인 → 커밋 여지 → 다음 청크
                         │                       │
                         └── 실패 ──► 자동 수정 → 재검증 (같은 실패 최대 3회, 초과 시 중단·보고)
```

### 1. 청크 선언
작업 전체를 논리적 청크(모듈 하나 / 서비스 하나 / 컨트롤러+엔드포인트 하나 / DTO+검증 / 엔티티+마이그레이션 / 가드·인터셉터 하나)로 쪼개 **TodoWrite로 나열**한다. 각 청크는 "그것만으로 검증 가능한 최소 단위"여야 한다.

### 2. 구현
현재 청크 하나만 구현한다. 구현 중 도메인 지식이 필요하면 해당 스킬(nestjs-crud·nestjs-database·nestjs-auth·nestjs-validation·nestjs-error-handling·nestjs-queue 등)을 호출해 따른다. (Service에 비즈니스 로직, Controller는 thin, DTO로 입력 검증 — 사용자 규칙.)

### 3. 정적 게이트 (항상 실행)
아래 순서로 돌린다. **앞 단계가 초록이어야 다음 단계로 간다**(타입이 깨진 채 테스트를 돌리는 것은 시간 낭비).

```
typecheck  →  lint  →  build  →  test
```

- **명령 탐지**: `package.json`의 `scripts`에서 자동 탐지한다.
  - typecheck: `typecheck` / `type-check` 스크립트, 없으면 `tsc --noEmit`
  - lint: `lint` 스크립트
  - build: `build` 스크립트(보통 `nest build`)
  - test: `test` 스크립트(nestjs-testing 기준 Vitest). watch가 기본이면 1회성으로 강제한다 — Vitest는 `vitest run`, Jest 프로젝트면 `--ci --watchAll=false`. 이번 청크 관련 스펙만 `-t`/경로로 좁혀 먼저 돌리고, 청크 끝에서 전체를 확정.
- **폴백**: 스크립트가 없으면 저장소 관례인 `pnpm build` / `pnpm test` / `pnpm lint`를 쓴다. (사용자 규칙상 **항상 pnpm**, npm 금지.)

### 4. 런타임/API 게이트 (요청 경로·부팅 동작이 바뀐 청크만)
정적 게이트가 초록이어도 앱이 실제로 뜨고 엔드포인트가 의도대로 응답하는지는 별개다. **런타임 동작이 바뀐 청크**(새 모듈·컨트롤러·엔드포인트·가드·프로바이더 배선·마이그레이션)라면 아래로 **스모크 체크**한다.

- ① **부팅되는가**: `Test.createTestingModule(...).compile()` 또는 앱 부팅이 에러 없이 성공하는가(DI 그래프 해석·모듈 등록 확인). 순환 의존성/미등록 프로바이더가 여기서 잡힌다.
- ② **엔드포인트가 응답하는가**: 새/변경 엔드포인트를 **supertest e2e**로 1건 호출해 기대 상태코드·응답 형태를 확인한다. e2e 세팅이 있으면 그것을 쓰고, 없으면 최소 e2e 스펙 하나로 이번 경로만 찌른다.
- ③ **계약이 지켜지는가**: 잘못된 입력에 검증(ValidationPipe) 에러가, 정상 입력에 기대 결과가 나오는가(해피 패스 1 + 실패 케이스 1).

순수 유틸·타입·설정만 바뀐 청크는 이 게이트를 건너뛴다(불필요한 비용).

**더 깊은 검증이 필요하면 위임한다** — 여기서 재구현하지 않는다:
- 유닛/e2e 테스트 본격 작성·모킹 전략·테스트 DB 세팅 → **nestjs-testing**
- 실 서버를 브라우저/외부에서 구동해 통합 확인 → **e2e-mcp**
- 런타임 관측(트레이스·메트릭·로그)로 동작 검증 → **grafana-observability**
- DB 마이그레이션 안전성·스키마 → **nestjs-database**

### 5. 실패 처리 (자동 수정 루프)
게이트가 실패하면 멈추지 말고 고친다.

1. 실패 출력을 읽고 원인을 특정한다.
2. 수정한 뒤 **실패한 그 게이트부터** 재실행한다.
3. 초록이면 다음 단계로, 아니면 반복한다.

**안전장치 — 무한 루프 방지:**
- **같은 실패가 3회 연속** 재현되면 자동 수정을 멈추고, 시도한 내용·현재 에러를 사용자에게 보고한 뒤 지시를 기다린다.
- 포맷/린트/단순 타입 오류처럼 명백한 것은 그냥 고친다. 그러나 **테스트 로직 자체가 틀렸는지, 도메인/아키텍처 결정이 필요한지**(트랜잭션 경계, 예외 매핑, 스키마 변경 등) 판단되는 실패는 3회를 기다리지 말고 조기에 멈추고 묻는다. (테스트를 통과시키려 도메인 의도를 왜곡하거나, 테스트를 무력화(skip/삭제)해서 초록을 만드는 것은 금지.)

### 6. 초록 확인 → 커밋 여지 → 다음 청크
- 모든 게이트가 초록이면 해당 Todo를 완료 처리한다.
- 사용자가 커밋을 원했거나 청크가 논리적 커밋 단위면, 이 지점이 자연스러운 커밋 포인트다(사용자 규칙: rebase 전용, imperative 메시지). 요청 없이 임의 커밋하지 않는다.
- 다음 청크로 이동해 2번부터 반복한다.

## 세션 예시

> 사용자: "주문 생성 API 만들어줘. 만들면서 검증해."

1. **청크 나열(TodoWrite)**: ① `Order` 엔티티 + 마이그레이션 ② `CreateOrderDto` + 검증 ③ `OrdersService.create` ④ `OrdersController` POST 엔드포인트 ⑤ 모듈 배선
2. **청크 ①**: 엔티티/마이그레이션 → typecheck·lint·build·test 초록 → 마이그레이션 up/down 검증 → ✅
3. **청크 ②**: DTO+class-validator → 정적 초록 → (요청 경로 아직 없음, 런타임 게이트 skip) → ✅
4. **청크 ③**: Service 구현 → 정적 초록 → 유닛 테스트(리포지토리 모킹) 해피/실패 1건씩 → ✅
5. **청크 ④~⑤**: 컨트롤러+모듈 배선 → 정적 초록 → **런타임 게이트**: 앱 compile 성공 + supertest로 `POST /orders` 201 + 잘못된 바디 400 확인 → ✅
6. 전체 청크 완료 후 마지막에 전체 test·build 한 번 확정.

## 이 스킬을 쓰지 않는 경우

- **테스트를 먼저 써서 구현을 이끌고 싶다** → `tdd`가 주도(레드-그린-리팩터). 이 스킬은 구현 후 게이트(test-after)다.
- **프론트엔드(React/Next.js) 작업** → `frontend-verify-loop`.
- **테스트 자체를 본격 작성·설정/모킹 전략** → `nestjs-testing`.
- **린트/포맷 도구 자체 설정** → `eslint`·`prettier`.
