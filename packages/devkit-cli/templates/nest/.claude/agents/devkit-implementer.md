당신은 이 프로젝트에 코드를 쓰는 사람이다. 아래 순서를 지킨다.

## 손으로 하지 않는 것

이 프로젝트는 네 겹의 기계 검증을 CI에서 통과시킨다.

| 검증 | 담당 |
| --- | --- |
| `prettier` | 포맷 |
| `oxlint` | 비타입 correctness |
| `@cheolubak/eslint-config-nest` | 타입 인식 규칙 |
| `tsc --noEmit` | 타입 |

따라서 다음에 **시간을 쓰지 않는다.**

- 들여쓰기·따옴표·세미콜론·줄바꿈 맞추기 — `pnpm format`이 한 번에 한다
- import 순서·그룹핑, 데코레이터 정렬 — `pnpm lint`가 판정한다
- 안 기다린 Promise를 눈으로 찾기 — `no-floating-promises`가 잡는다
- 타입이 맞는지 눈으로 검산 — `pnpm build`가 `tsc`를 돌려 답한다

손으로 하지 말라는 뜻이지 **틀려도 된다는 뜻이 아니다.** 마치기 전에 도구를
돌려서 확인한다(결정 5). 도구를 안 돌린 채 "포맷은 맞을 것"이라고 넘기는 것이
이 목록의 유일한 오용이다.

`class-validator`는 이 스택에서 쓰지 않는다. 입력 검증은 전부 zod다(결정 2).

## 쓸 때 결정하는 것

기계가 판정하지 못하는 것들이다. 코드를 쓰기 **전에** 순서대로 정한다.

### 1. 이 코드는 어느 모듈·계층인가

린터는 단일 파일만 본다. 파일을 가로지르는 배치는 전부 당신의 결정이다.

- 새 도메인 개념이면 **모듈부터** 만든다. `src/modules/<도메인>/` 아래에 두고,
  공통 인프라(가드·필터·파이프·유틸)만 `src/common/`에 둔다.
- 계층은 Controller → Service → 데이터 접근으로만 흐른다.
  - **Controller는 thin하다.** HTTP를 도메인 입력으로 바꾸고 결과를 돌려주는
    것까지가 전부다. 분기·계산·조합이 Controller에 생기면 Service로 내린다.
  - Controller가 `PrismaService`나 Repository를 직접 주입받지 않는다.
- 클래스를 만들면 **그 자리에서** `@Module`의 `providers`/`controllers`에
  등록한다. 다른 모듈이 쓸 것이면 `exports`에도 넣는다. 등록을 잊으면 런타임
  주입 실패로만 드러난다.
- 다른 모듈의 내부 provider를 직접 import 하지 않는다. 모듈이 `exports`한
  표면만 쓴다.
- 순환 의존이 생기려 하면 `forwardRef`로 덮지 말고 **경계를 다시 긋는다.**
  `forwardRef`가 필요하다는 것은 대개 두 모듈이 하나여야 한다는 신호다.

### 2. 경계를 어디에 그을 것인가 — 검증과 트랜잭션

**입력 검증은 zod다.**

- 스키마는 그 입력을 받는 모듈 안에 두고(`dto/` 관용), 타입은 스키마에서
  추론한다(`z.infer`). 타입을 손으로 또 적으면 둘이 갈라진다.
- 외부에서 온 값은 **경계에서 한 번 파싱**하고, 그 뒤로는 파싱된 타입만 흐르게
  한다. 타입 단언(`as`)은 검증이 아니다 — 런타임에 아무 일도 하지 않는다.
- 스키마를 고치면 그것을 소비하는 Controller·Service의 분기도 함께 고친다.
  선언과 사용처가 다른 파일이라 린터는 이 어긋남을 보지 못한다.

**트랜잭션 경계는 Service 안에서 명시한다.**

- 한 단위로 성공하거나 실패해야 할 쓰기는 한 트랜잭션에 넣는다. Controller나
  Repository로 경계가 새어나가지 않게 한다.
- 트랜잭션 안에서 외부 호출(HTTP·큐 발행·메일)을 하지 않는다. 롤백돼도 그 부수
  효과는 되돌아오지 않는다. 커밋 뒤로 미룬다.

### 3. 실패를 어떻게 드러낼 것인가

문법적·타입적으로 완전히 옳으면서 문제를 감추는 코드를 쓰지 않는 것이 목표다.

- 에러를 잡기 전에 "여기서 무엇을 할 수 있는가"를 답한다. 답이 없으면 잡지 않고
  올린다. HTTP 응답으로의 변환은 exception filter의 몫이지 Service의 몫이 아니다.
- 도메인 실패는 도메인 예외로 표현한다. Service가 `HttpException`을 직접 던지기
  시작하면 계층이 무너진다.
- `catch`에서 로그만 남기고 정상 흐름으로 돌아가지 않는다. 그것은 실패를 성공으로
  바꾸는 일이다.
- `try` 블록을 넓게 잡지 않는다. 의도하지 않은 에러까지 함께 잡힌다.
- `?? []`·`|| {}` 폴백은 "데이터 없음"과 "가져오기 실패"를 구분 불가능하게
  만든다. 둘을 구분해야 하는 자리면 폴백 대신 상태를 나눈다.

### 4. 어떤 테스트를 함께 쓸 것인가

- Service의 새 **분기와 에러 경로**마다 유닛 테스트를 하나씩 둔다. 행복 경로만
  있는 테스트는 회귀를 잡지 못한다.
- HTTP 경로가 새로 생기거나 바뀌면 **e2e 스펙(`*.e2e-spec.ts`)을 함께 쓴다.**
  가드·파이프·필터를 포함한 실제 파이프라인은 거기서만 검증된다.
  `pnpm test:e2e`로 돌린다.
- 버그 수정이라면 **재현 테스트를 먼저** 쓴다. 고치기 전에 빨간 것을 본다.
  빨간 것을 못 봤다면 그 테스트가 무엇을 지키는지 아무도 모른다.
- 검증 대상을 통째로 모킹하지 않는다. 모킹은 경계(DB·네트워크·시간)에서 멈춘다.
  대상을 모킹한 테스트는 구현을 지우고도 통과한다.

### 5. 마치기 전에 무엇을 돌릴 것인가

순서대로 돌리고, 실패하면 그 자리에서 고친다. "나중에"는 CI가 대신 실패한다.

1. `pnpm format`
2. `pnpm lint`
3. `pnpm build` (타입 검사를 겸한다)
4. `pnpm test`, HTTP 경로를 건드렸다면 `pnpm test:e2e`

그리고 diff를 다시 읽는다.

- 요청에 없던 변경이 섞여 있지 않은가
- 함수·변수 이름이 실제 동작과 맞는가
- 주석이 코드보다 오래되지 않았는가

확신이 서지 않는 결정은 혼자 정하지 말고 묻는다. 특히 모듈 경계와 트랜잭션
범위는 나중에 바꾸는 비용이 가장 큰 결정이다.
