당신은 이 프로젝트에 코드를 쓰는 사람이다. 아래 순서를 지킨다.

## 손으로 하지 않는 것

이 프로젝트는 네 겹의 기계 검증을 CI에서 통과시킨다.

| 검증 | 담당 |
| --- | --- |
| `prettier` | 포맷 |
| `oxlint` | 비타입 correctness |
| `@cheolubak/eslint-plugin-fsd` | FSD 레이어 간 import 방향 |
| `tsc --noEmit` | 타입 |

따라서 다음에 **시간을 쓰지 않는다.**

- 들여쓰기·따옴표·세미콜론·줄바꿈 맞추기 — `pnpm format`이 한 번에 한다
- import 순서·그룹핑 정렬 — `pnpm lint`가 판정한다
- 레이어 간 import 방향이 맞는지 손으로 추적 — `eslint-plugin-fsd`가 판정한다
- 타입이 맞는지 눈으로 검산 — `pnpm typecheck`가 답한다

손으로 하지 말라는 뜻이지 **틀려도 된다는 뜻이 아니다.** 마치기 전에 도구를
돌려서 확인한다(결정 5). 도구를 안 돌린 채 "포맷은 맞을 것"이라고 넘기는 것이
이 목록의 유일한 오용이다.

## 쓸 때 결정하는 것

기계가 판정하지 못하는 것들이다. 코드를 쓰기 **전에** 순서대로 정한다.

### 1. 이 코드는 어느 레이어인가

`eslint-plugin-fsd`는 레이어 **간 import 방향**만 본다. **이 코드가 애초에 어느
레이어에 있어야 하는지**는 판정하지 못한다. 그것이 당신의 결정이다.

"누가 이것을 쓰는가"를 먼저 답하면 레이어가 따라온다.

| 답 | 레이어 |
| --- | --- |
| 특정 화면 하나의 조합 | `views` (FSD의 페이지 레이어) |
| 여러 화면이 쓰는 자체 완결 UI 블록 | `widgets` |
| 사용자가 하는 행위 — 로그인, 담기, 검색 | `features` |
| 도메인 개념 자체와 그 표현 — User, Post | `entities` |
| 도메인을 전혀 모르는 유틸·프리미티브 UI | `shared` |

- `shared`는 "일단 여기"가 아니다. 도메인을 아는 순간 `shared`가 아니다.
- 라우팅은 `src/app/`, 화면 조합은 `src/views/`다. `app/page.tsx`는 `views`
  슬라이스를 불러 쓰는 얇은 층으로 둔다. 둘을 섞지 않는다.
- 슬라이스를 만들 때 `index.ts`(public API)를 **먼저** 쓴다. 밖으로 낼 것만
  거기서 export 하고, 다른 슬라이스는 내부 파일을 직접 import 하지 않는다.
- 확신이 서지 않으면 더 아래가 아니라 **더 위**에 둔다. 위에서 아래로 내리는
  것은 언제든 되지만, 아래에서 위로 올릴 때는 이미 여러 곳이 의존한 뒤다.

### 2. 경계를 어디에 그을 것인가 — Server/Client

- Server Component가 기본이다. `'use client'`를 붙이기 전에 이유를 한 문장으로
  댄다: 상태인가, 이벤트 핸들러인가, 브라우저 API인가, 클라이언트 전용 훅인가.
  넷 다 아니면 붙이지 않는다.
- `'use client'`는 **잎(leaf)에 붙인다.** 트리 위쪽에 붙이면 그 아래 전체가
  클라이언트가 된다. 상호작용하는 조각만 떼어내 그 조각에 붙인다.
- 서버 전용 값(토큰·API 키·DB 핸들)은 클라이언트 컴포넌트의 props로 넘기지
  않는다. props는 직렬화되어 브라우저로 간다.
- mutation은 Server Action으로 처리한다. Server Action의 인자는 **클라이언트에서
  온 값**이므로 zod로 파싱한 뒤 쓴다. 타입 단언(`as`)은 검증이 아니다 — 런타임에
  아무 일도 하지 않는다.

### 3. 실패를 어떻게 드러낼 것인가

문법적·타입적으로 완전히 옳으면서 문제를 감추는 코드를 쓰지 않는 것이 목표다.

- 에러를 잡기 전에 "여기서 무엇을 할 수 있는가"를 답한다. 답이 없으면 잡지 않고
  올린다. 잡을 곳은 대개 호출부가 아니라 경계다.
- `catch`에서 로그만 남기고 정상 흐름으로 돌아가지 않는다. 그것은 실패를 성공으로
  바꾸는 일이다.
- `?? []`·`|| {}` 폴백은 "데이터 없음"과 "가져오기 실패"를 구분 불가능하게
  만든다. 둘을 구분해야 하는 자리면 폴백 대신 상태를 나눈다.
- 로딩·에러·빈 상태를 성공 UI 하나로 뭉개지 않는다. App Router의 `loading.tsx`·
  `error.tsx`가 그 자리다.

### 4. 어떤 테스트를 함께 쓸 것인가

- 새로 만든 **분기와 에러 경로**마다 테스트를 하나씩 둔다. 행복 경로만 있는
  테스트는 회귀를 잡지 못한다.
- 버그 수정이라면 **재현 테스트를 먼저** 쓴다. 고치기 전에 빨간 것을 본다.
  빨간 것을 못 봤다면 그 테스트가 무엇을 지키는지 아무도 모른다.
- 검증 대상을 통째로 모킹하지 않는다. 모킹은 경계(네트워크·시간·랜덤)에서 멈춘다.
  대상을 모킹한 테스트는 구현을 지우고도 통과한다.
- 러너는 vitest다 — `pnpm test`, 개발 중에는 `pnpm test:watch`.

### 5. 마치기 전에 무엇을 돌릴 것인가

순서대로 돌리고, 실패하면 그 자리에서 고친다. "나중에"는 CI가 대신 실패한다.

1. `pnpm format`
2. `pnpm lint`
3. `pnpm typecheck`
4. `pnpm test`

그리고 diff를 다시 읽는다.

- 요청에 없던 변경이 섞여 있지 않은가
- 컴포넌트·훅 이름이 실제 동작과 맞는가
- 주석이 코드보다 오래되지 않았는가

확신이 서지 않는 결정은 혼자 정하지 말고 묻는다. 특히 레이어 배치는 나중에
바꾸는 비용이 가장 큰 결정이다.
